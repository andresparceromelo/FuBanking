Arranque del REPL

Las unidades del módulo se parten en dos según sus dependencias, y el protocolo las trata por separado porque el grado de aislamiento no es el mismo.

ParteQué contieneAislamientoCasos
A Entidades Pocket y Account, y los schemas de validación Total: no colaboran con nada, no hay qué sustituir 32
B Los cinco casos de uso del módulo Aislados de Express, rutas, middleware y Zod; no de la base de datos 37
Sobre el aislamiento de la Parte B. Los casos de uso reciben los repositorios por constructor: no se pueden instanciar sin pasarles algo. Se les inyectan los repositorios Supabase reales, no dobles. Un fallo en la Parte B puede originarse en el caso de uso o en el repositorio, y hay que distinguirlo al registrar el resultado. La Parte A no tiene esa ambigüedad.

Lo que se gana respecto de probar por HTTP

Al invocar el método directamente, los schemas Zod no intervienen. Tres ramas de error que por HTTP eran inalcanzables aquí sí se ejecutan: las cubren CU-CR-01, CU-AC-03 y CU-TR-01.

Abrir el REPL

# desde una terminal interactiva: el REPL solo abre si hay TTY
cd backend
npx tsx

Al primer require que cargue la configuración aparece una línea como ◇ injected env (10) from .env: es dotenv leyendo backend/.env, es normal. Si en cambio el proceso se cierra solo, ese archivo está incompleto — env.ts valida las variables y llama a process.exit(1).

Por qué todo va con var. Los casos se escriben uno tras otro en la misma sesión y varios reutilizan el mismo nombre. Con const el segundo fallaría con Identifier has already been declared y habría que reiniciar la sesión. var admite redeclaración.

Preparación 5 pasos · no cuentan en el marcador

B-SETUP-01 · Obtener el USER_ID

Usar un usuario que ya exista. Buscarlo por correo y copiar su id:

ver(usrRepo.findByEmail('tu-correo@ejemplo.com'))

var USER_ID = '...'
var FAKE = '00000000-0000-4000-8000-000000000000'

AJENO no necesita existir: assertBelongsTo compara el userId del DTO contra el dueño de la cuenta y lanza antes de consultar nada más. Por eso no hace falta registrar un segundo usuario para los casos de autorización.

B-SETUP-05 · (Opcional) Cuenta bloqueada

Ni la API ni los casos de uso exponen forma de bloquear una cuenta, así que el estado se cambia a mano: Supabase → Table editor → tabla accounts → fila ACC3 → columna status de ACTIVA a BLOQUEADA. Solo hace falta para CU-CR-08; si se omite, ese caso se marca Bloqueado. Devolver ACC3 a ACTIVA antes de CU-CO-04.

Limpieza posterior

Los datos de la Parte B quedan en la base real. Desde el Table editor de Supabase, en este orden:

  1. pockets — borrar las filas cuyo account_id sea ACC1, ACC2 o ACC3.
  2. notifications — borrar las notificaciones de tipo BOLSILLO generadas en la corrida.
  3. account_details y luego accounts — borrar las tres cuentas.

El usuario no se toca: se reutilizó uno existente.

Hallazgos
