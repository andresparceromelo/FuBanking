Entorno y convenciones

Cada caso recorre PocketController → validadores Zod → caso de uso → repositorio Supabase. En rigor son pruebas de integración de componente, aunque el diseño de los casos sea de caja blanca: cada uno se derivó de una decisión concreta del código.

Antes de empezar

# terminal 1 — levantar el backend
cd backend && npm run dev

# terminal 2 — comprobar que responde
curl -s http://localhost:3001/health

Debe devolver {"status":"ok", ...}. Si no responde, ningún caso de este protocolo es ejecutable.

Advertencia. Estas pruebas escriben en la base de datos real: crean usuarios, cuentas, bolsillos y notificaciones que quedan persistidos. Ejecutarlas contra un proyecto de Supabase de desarrollo, nunca contra producción.

Formato de respuesta

// éxito
{ "success": true, "message": "<mensaje>", "data": <objeto o arreglo> }

// error
{ "success": false, "error": { "code": "<CODIGO>", "message": "<mensaje>" } }

Los errores de Zod agregan error.fields con el detalle por campo.

Vocabulario de saldos

La invariante del módulo: disponible (accounts.balance) más reservado (suma de los bolsillos) debe ser siempre igual al total depositado. Cada caso declara el estado esperado antes y después en esos términos.

Limpieza posterior

Los datos quedan en la base real. Para dejarla como estaba, desde el Table editor de Supabase y en este orden:

  1. pockets — borrar las filas cuyo account_id sea una de las cinco cuentas de prueba.
  2. notifications — borrar las filas de los dos usuarios de prueba.
  3. transactions — borrar los depósitos del paso SETUP-05.
  4. account_details y luego accounts — borrar las cinco cuentas.
  5. users — borrar qa.bolsillos.a@fubank.com y qa.bolsillos.b@fubank.com.

Alternativa: conservar los usuarios de prueba para la siguiente corrida y borrar solo bolsillos y cuentas.

Hallazgos

Detectados al diseñar los casos a partir del código. Ninguno se corrigió en esta entrega: el alcance acordado era corregir las pruebas, no el código de producción.

H-01

El saldo reservado se cuenta dos veces al crear un bolsillo

Alta

Caso que lo evidencia: BE-CR-13 · CreatePocket.ts

La decisión es currentReserved + dto.amount > account.balance, pero account.balance ya es el saldo disponible: lo reservado se descontó al crear los bolsillos anteriores. La comparación suma el reservado a un valor que ya lo excluye, así que se rechazan bolsillos que sí caben. En cuanto lo reservado supera lo disponible, no se puede crear ningún bolsillo nuevo, ni siquiera de $1.

UpdatePocket resuelve el mismo problema correctamente, comparando contra account.balance + totalReserved. Las dos operaciones aplican reglas distintas al mismo invariante.

H-02

Cuatro ramas de error del dominio son inalcanzables por HTTP

Media

Casos que lo evidencian: BE-CR-03, BE-AC-02, BE-AC-03, BE-TR-02

Los schemas Zod validan las mismas condiciones que los casos de uso y siempre disparan primero, así que el cliente recibe VALIDATION_ERROR donde el diseño del dominio anunciaba un código específico.

Rama del caso de usoBloqueada por
CreatePocket → INVALID_POCKET_AMOUNTcreatePocketSchema.amount.min(0)
UpdatePocket → INVALID_POCKET_AMOUNTupdatePocketSchema.amount.min(0)
UpdatePocket → NO_CHANGES_PROVIDEDupdatePocketSchema.refine(...)
TransferPocketBalance → INVALID_TRANSFER_AMOUNTtransferPocketSchema.amount.gt(0)

La única excepción es UpdatePocket → INVALID_POCKET_NAME, alcanzable con un nombre de solo espacios (BE-AC-04), porque Zod valida longitud pero no contenido.

H-03

Validación de identificadores inconsistente entre endpoints

Baja

Casos que lo evidencian: BE-AC-06, BE-EL-03, BE-TR-04

POST /pockets y POST /pockets/transfer validan los UUID con Zod y responden 400 VALIDATION_ERROR. PATCH, DELETE y GET toman el identificador de la ruta, no lo validan, y responden 404 porque el repositorio convierte el error de Supabase en null. La misma clase de entrada inválida produce dos códigos distintos.

H-04

No hay forma de bloquear una cuenta desde la API

Baja

Casos afectados: BE-CR-08, BE-AC-08, BE-EL-05, BE-TR-10

La entidad Account expone block() y close(), y los cuatro casos de uso comprueban isOperational(), pero ninguna ruta permite cambiar el estado de una cuenta. Los caminos ACCOUNT_NOT_OPERATIONAL solo se pueden probar editando la columna status a mano en Supabase.

H-05

El repositorio de bolsillos tiene un modo de respaldo en memoria

Media

Ubicación: SupabasePocketRepository.ts

Si la tabla pockets no existe, el repositorio activa un fallbackStore en memoria a nivel de módulo y sigue operando. Con esa bandera activa los datos no se persisten y se pierden al reiniciar el servidor, mientras la API sigue respondiendo 201 y 200.

Antes de dar por válida una corrida, revisar la consola del backend. Si aparece "Supabase pockets table is not available. Using in-memory fallback for pockets.", toda la corrida queda invalidada: se estaría probando contra memoria, justo lo que este protocolo busca evitar.
